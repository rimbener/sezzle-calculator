Layering, as `spec.md` § Approach lays it out: `src/app.ts` parses, calls and serialises, nothing else — `createApp({ calculate })` with the domain's `calculate` as the default, `app = createApp()`; `STATUS_BY_CODE: Record<ErrorCode, ContentfulStatusCode>` is the one status-per-code table (a new code is one entry, and `tsc` rejects a missing one — cycle 2 shows it); `fail(c, code, message)` is the only way an error leaves, always as the contract's envelope; `app.onError` maps `CalculationError` → its own code (422) and anything else → `INTERNAL_ERROR` (500). The body is read as text and `JSON.parse`d by hand so a syntax failure is the contract's `INVALID_JSON_MESSAGE`, not an exception (`JSON.parse` never yields `undefined` for valid JSON, so that is an unambiguous sentinel). `src/config.ts` is `resolvePort(env)`, a pure function of an environment object; `src/server.ts` exports `start(env)` (resolves once listening, returns `{ port, close }` with `port` read from the listener's `AddressInfo` — the port actually bound, not the one requested) and binds only under `import.meta.main` (Node 24.20 supports it; typed in `@types/node` 24).

## Observations for the reviewer (not findings, no test demanded them)

- `app.onError` replaces Hono's default handler, which also `console.error`s the error; the 500 path here logs nothing, so an unexpected failure is visible only as the response. No criterion asks for operator logging.
- `resolvePort` does not validate the variable: `CALC_SERVICE_PORT=abc` yields `NaN` and `serve` rejects; `CALC_SERVICE_PORT=` (empty) is `Number("") === 0`, an OS-chosen port — which `start` now reports as bound (F-1). AC-15 covers absent and set-to-a-port only.
- `server.ts` binds on Node's default host (all interfaces); the spec fixes no hostname for the internal service.
