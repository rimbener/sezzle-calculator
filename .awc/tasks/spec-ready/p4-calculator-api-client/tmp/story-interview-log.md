# story-interview-log — p4-calculator-api-client

## From the source
### Settled
- who — the end user of the calculator SPA (`docs/PRD-P0.md` §5 Users, US-1..US-7); no new persona.
- what — a typed API client module and a hook that wires it to the phase-3 state machine's `onRequest` seam, so pressing `=` or `sqrt` actually reaches the gateway; a busy indicator while a call is pending; a clear, non-technical message for each of the four failure kinds FE-4 names (domain error, backend outage, network failure, unexpected response). (`docs/PRD-P0.md` FE-2, FE-4, FE-5, FE-7; `docs/spec-phases.md` phase 4 in-scope list.)
- why — FE-2 forbids local arithmetic, and `p3-calculator-ui`'s spec left `=` a dead end on purpose ("pressing `=` in `npm run dev` freezes the calculator until the page is reloaded... Phase 4 makes the app whole"); this task is what removes that limitation and completes the assessment's end-to-end path.
- when/where — `apps/sezzle-calculator`; triggered the same way phase 3 already triggers a request — pressing `=` (binary ops) or an operation key that fires immediately (`sqrt`). No new UI surface: this task extends `Calculator`'s existing `onRequest` prop and `Display`'s existing `busy` state, both already named in `state.ts`/`display.tsx` as phase-4's seam.
- success — (a) a valid calculation shown as the result over the completed expression, sourced from the real gateway response; (b) a pending call shows the busy indicator and a second `=`/unary press while pending sends no extra request (already structurally guaranteed by the reducer's frozen `pending` status — this task supplies the visible indicator FE-5 also asks for); (c) each of the four failure kinds shows its own message, never a blank screen, frozen state, or raw exception; (d) an error clears on the next valid input (already the reducer's `settled` transition — the client only has to supply the message the outcome carries).
- edges — domain errors (422: `DIVISION_BY_ZERO`, `NEGATIVE_SQRT`, `RESULT_NOT_FINITE`) show the message the contract already fixes for each code; backend outage (502/504 `SERVICE_UNAVAILABLE`, calc-service down or timing out behind the gateway) shows "Calculations are temporarily unavailable — try again" (FE-4's own quote); a network failure (the gateway itself unreachable, `fetch` throws) shows "Can't reach the calculation service — try again" (UC-8's own quote); anything that fails to match the shared response/error schemas is the unexpected-response case, which FE-4 names but for which no PRD text fixes exact copy — its wording is a solution-level decision (copy), left to the spec step, the same way phase 3 left all error copy to phase 4 rather than asking the human at the story stage.
- surface — `apps/sezzle-calculator` only: the new client module, the new hook, and `App.tsx`/`Calculator` wiring. Phase 3's reducer, key model, and display projection are extended, never respecified (`docs/spec-phases.md`: "the input state machine and the key/display components — extend them, do not respec them").
- collisions — none against a locked decision. This task implements exactly the boundary `p3-calculator-ui`'s spec already locked: `onRequest` resolves with `CalculateResponse | ErrorResponse` and never rejects; the reducer already freezes every key during `pending`; `Display`'s `busy` state already exists and was explicitly deferred here ("`state="busy"` is deferred to Phase 4").
