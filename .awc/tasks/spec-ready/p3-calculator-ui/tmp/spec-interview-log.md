# Spec interview — p3-calculator-ui

## 1 — surfaces and reshaping
Q: Two facts from the repo set this up. `apps/sezzle-calculator/src/App.tsx` today renders nothing but `<DesignSystem />` — the component gallery from `@repo/ui` — so the app has no calculator in it at all. And `@repo/ui` already exports `Key` (with `number`/`operator`/`function`/`equals`/`clear` faces) and `Display` (with `value`, `expression`, `hint` and an `idle`/`busy`/`error` state), but it has **no keypad-grid component and no pad CSS** — `components.css` styles individual keys, never their arrangement. So two calls, and they go together. First: does the keypad grid become a new `@repo/ui` component with its classes in `packages/ui/src/styles/components.css` (which is what `CLAUDE.md` prescribes for new design-system components, and it keeps the pad reusable in the gallery), or does the arrangement live in `apps/sezzle-calculator` with the app's own CSS, leaving `@repo/ui` untouched as a component vocabulary? Second: what happens to the `<DesignSystem />` gallery — App.tsx becomes the calculator and the gallery is dropped from the app entirely, or the gallery stays reachable somehow alongside it?
A: a, and <DesignSystem /> is dropped from the app entirely

## 2 — display semantics
Q: What the display actually shows, which every acceptance criterion in this phase asserts against. `@repo/ui`'s `Display` has two text slots: a large `value` (the LCD readout) and a small `expression` line above it. Take the sequence `1`, `2`, `+`, `5`, `=`. The `value` slot obviously shows `12`, then `5`, then the result. My question is the two moments in between. (i) Right after `+` is pressed and before any second digit, does `value` still show `12`, or does it reset to `0` to signal that a new operand is expected? (ii) Is the `expression` line used at all in this phase — showing the calculation being built, e.g. `12 +` and then `12 + 5` — or does it stay empty, leaving `value` as the only thing that changes? Option (i)-keeps-`12` with a populated `expression` is the classic desk-calculator feel; `value` resetting to `0` with an empty `expression` is the cheapest to describe but the user briefly loses sight of what they typed.
A: Keep 12 with a populated expression is the classic desk-calculator feel

## 3 — display semantics
Q: Following that through to the moments after `=`, because the criteria have to assert the expression line's exact contents. With `12 + 5` entered and `=` pressed, the outcome comes back and `value` shows `17`. What does the `expression` line show at that instant — (a) the completed calculation, `12 + 5 =`, so the user can still read what produced the 17; or (b) it clears, leaving the result standing alone? And then, since a digit pressed on a result starts a fresh entry (settled in the story), pressing `3` next gives `value` `3` — does the expression line clear at that point under (a), or does the fresh entry only clear it once an operator is pressed? For `sqrt`, which fires on the key press, the equivalent question is whether the expression reads `sqrt(9)` while the result stands.
A: a, and pressing 3 next gives value 3

## 4 — display semantics
Q: Two leftovers from that same line, both of which a criterion has to assert. (i) With `12 + 5 =` on the expression line and `17` in the value, pressing `3` makes the value `3` — at that same instant does the expression line clear to empty, or does it keep showing `12 + 5 =` until an operator is pressed? Clearing immediately means the display never shows a stale calculation next to an unrelated number; keeping it means the user can still see what they just did while typing the next number. (ii) For `sqrt`, which fires on the key press: with `9` entered and `sqrt` pressed, the value becomes `3` — does the expression line read `sqrt(9) =`, matching the `12 + 5 =` shape, or something else?
A: i: clean. II: yes

## 5 — pending semantics
Q: The `pending` state. This phase builds the state machine that occupies it, while the thing that actually performs the call — and the visible busy indicator — is Phase 4's. So the machine has to define what a key press does between emitting a request and an outcome coming back, and that is behaviour this phase owns and tests. Three ways: (a) every key is ignored while pending except `C`, which cancels back to the starting state and makes any late outcome irrelevant; (b) every key is ignored while pending, `C` included, so the machine is fully frozen until an outcome arrives; (c) keys are accepted and applied normally while pending — the user can keep typing, and the outcome lands on whatever state exists by then. (c) is the most permissive but means an outcome can arrive into an entry the user has already moved past, which the machine then has to decide what to do with. Which behaviour do you want?
A: b

## 6 — error recovery semantics
Q: Error recovery. The story settles that an error outcome keeps the input so it can be corrected and clears on the next valid input, but not what "corrected" means concretely, and a criterion has to say. Take `5`, `/`, `0`, `=` — the outcome comes back as a division-by-zero error. The machine is now holding `5 / 0`. The user presses `3`. Does that (a) replace the bad second operand, so the state becomes `5 / 3` and a following `=` calculates that — the reading that makes "correct it" literal; or (b) start a completely fresh entry, so the display becomes just `3` and the whole `5 / 0` is discarded — the same rule a digit follows after a successful result? And separately: while the error is being held, does the display's value slot keep showing `0` (the operand that caused it) with the expression still reading `5 / 0 =`, or does it show something else? Only the state matters here, not the wording — the error copy itself is Phase 4's.
A: b, and error message

## 7 — error presentation and the phase boundary
Q: "Error message" needs one more turn, because `docs/spec-phases.md` puts the error copy itself in Phase 4 ("error message copy and the busy indicator") while this phase owns the state. The way to have both is for the error outcome handed to the machine to **carry** its message, and for this phase to render whatever string it carries without deciding any of the strings — Phase 4 then supplies the real wording with no UI change. Is that what you want? If so, the last detail is where it renders, since `@repo/ui`'s `Display` has three slots: the large `value`, the small `expression` above it, and a `hint` line below. With `5 / 0 =` having failed, I would put the carried message in `hint`, switch the Display to its `error` state, leave `expression` reading `5 / 0 =`, and leave `value` showing `0` — so the numbers stay visible and the message sits under them. Does that match what you meant, or should the message take over the `value` slot instead?
A: yes, and the message should take over the value

## 8 — entry validation semantics
Q: The digit cap. FE-3 says "maximum 15 significant digits", and the criterion has to be exact about what gets counted, because three readings give different answers for the same key presses. Typing `0.000123456789012345`: (a) **significant digits in the mathematical sense** — leading zeros do not count, so `0.000` is free and the user gets 15 digits after them; (b) **digit characters entered for this operand** — every `0` counts, so the leading `0.000` eats four of the fifteen; (c) **total characters in the operand**, so the decimal point counts too and the cap is really 15 characters. (a) is the literal reading of FE-3 and the most generous; (b) is the simplest to implement and to explain in a test; (c) is what a physical calculator's 15-cell display actually does. Which one is the cap, and does the already-settled leading-zero absorption change your answer — with `007` collapsing to `7`, those absorbed zeros never reach the operand at all?
A: c

## 9 — escalation: what the running app does at `=` with no caller
Q: An escalation, because it is a collision between two things already settled and I will not pick for you. Nothing in this phase performs the call, and you chose (b) for pending: the machine freezes completely, `C` included, until an outcome arrives. In the unit tests that is fine — they hand outcomes to the machine directly. But in the app a human runs with `npm run dev`, pressing `=` emits a request that nobody answers, so the calculator freezes for good and even `C` will not recover it, until the page is reloaded. `docs/spec-phases.md` says "every phase leaves the repo working and testable", which that arguably breaks. Three ways out, and my recommendation is (a). (a) Accept it and be explicit: this phase's deliverable is the UI plus a fully tested machine, the dev app is a preview where `=` is a dead end until Phase 4 lands, and the spec says so in as many words — no throwaway code, nothing to unpick later. (b) Relax pending to let `C` cancel after all — one line, the app always recovers, but it contradicts the answer you just gave and Phase 4 would have to decide what a late outcome does to a cancelled entry. (c) Ship a temporary stand-in outcome source in the app so `=` visibly resolves — which would mean doing the arithmetic locally, the one thing this phase forbids, and deleting it again in Phase 4. Which?
A: a

## 10 — sqrt mid-expression
Q: One gap I found while modelling the machine, and it is the last thing I need. `sqrt` is the only one-operand operation, and it fires on the key press rather than waiting for `=`. That is unambiguous on its own — enter `9`, press `sqrt`, get `3`. What is undefined is `sqrt` pressed while a two-operand expression is half built. The user types `12`, presses `+` (so the value slot still shows `12` and the expression reads `12 +`), then presses `sqrt`. The general rule says an operation key replaces the recorded operation, but `sqrt` needs only one operand, so it cannot wait. Three readings: (a) it takes the currently displayed value and fires — `sqrt(12)` — silently discarding the pending `+`, so the display goes to `3.464...` with the expression `sqrt(12) =`; (b) it is refused like any other invalid press — silently ignored, the `12 +` stands, and `sqrt` only works when no operation is pending; (c) it applies to the second operand once one has been typed — `12`, `+`, `5`, `sqrt` gives `sqrt(5)` whose result becomes the second operand, so a following `=` computes `12 + 2.236...`, and pressing `sqrt` with no second operand yet is refused. Which?
A: b

_Every area is settled; the bundle was written from this log._
